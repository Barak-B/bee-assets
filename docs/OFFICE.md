# מסך משרד, כרטיס לקוח ומפתחות אישיים

מה שהמשרד צריך כדי לנהל עבודות בלי לעלות על הגג: כל העבודות במקום אחד, איפה כל אחת עומדת, ומה דורש טלפון היום.

## איפה

`https://app.barak-e.com/office` — אותו פרויקט Pages ואותו אחסון כמו האפליקציה, בלי הגדרה נוספת. נכנסים עם **מפתח משרד או מנהל**. המפתח נשמר בדפדפן הזה בלבד ("יציאה" מוחק אותו).

## מה רואים

| חלק | מה יש בו |
|---|---|
| **מספרים** | עבודות פעילות · ממתינות לאישור (וסכומן) · אושרו ב-30 יום (וסכומן) · **דורשות טיפול** |
| **שלבים** | סקר → הצעה → נשלח ללקוח → הלקוח אישר → בהתקנה → נמסר. לחיצה מסננת |
| **טבלה** | פרויקט ולקוח (טלפון לחיץ), שלב והצעד הבא, הצעה אחרונה (סכום, kWp, "לאימות"), קישור (נפתח / טרם נפתח / אושר), דוחות (וכשל אם יש), סוקר, פעילות אחרונה |
| **חיפוש** | שם, לקוח, טלפון (בכל כתיב: `050-1234567` = `+972501234567`), כתובת, מספר הצעה |
| **פרטי עבודה** | לקוח (טלפון, וואטסאפ, מייל) · כל הקישורים שפורסמו (גם מבוטלים), צפיות, אישור הלקוח ואם ה-ת״ז אומתה · דוחות שטח ותוצאתם · פרטי הסקר ותמונות · **סטטוס משרד והערה** |

## עבודה חדשה מהמשרד ושיבוץ סוקר

**"+ עבודה חדשה"** במסך המשרד: לקוח, טלפון, כתובת (חובה), מייל, שם פרויקט, הערה לסוקר, סוקר ומועד סקר.

1. העבודה נפתחת בשלב **ממתין לסקר**.
2. הטלפון של הסוקר המשובץ מושך אותה בסנכרון הבא שלו: מיד ב"סנכרן לשרת", או תוך 10 דקות לכל היותר ברקע. מופיעה הודעה "עבודה חדשה מהמשרד".
3. בטלפון הסקר כבר ממולא: לקוח, טלפון, כתובת, מועד והערה. ברשימה רואים "ממתין לסקר · 📅 22.10".
4. מהרגע שהסוקר עובד עליה, עותק הטלפון הוא הסקר. המשרד ממשיך לנהל רק את השיבוץ, המועד, הסטטוס וההערה, שנשמרים בנפרד.
5. **שיבוץ מחדש:** בפרטי העבודה בוחרים סוקר אחר. הטלפון של הסוקר החדש מושך את העבודה בסנכרון הבא.

אפשר לשבץ רק מי שיש לו מפתח אישי פעיל, ולכן שובץ ב-`PUBLISH_KEY` לא קיים.

רק עבודה **פעילה** יורדת לטלפון. עבודה מוקפאת, לא רלוונטית או סגורה לא יורדת. סוקר שמחק אצלו עבודה שעדיין פעילה ומשובצת לו יקבל אותה שוב בסנכרון הבא. כדי שלא תחזור, מבטלים את השיבוץ או משנים את הסטטוס במשרד.

## איך נקבע השלב: מחזור החיים S01–S12

**השלב לא מוזז ביד.** הוא נגזר ממה שקרה בפועל, באותו קוד בשרת ובאפליקציה (`apps/bee-solar-survey/src/stage.ts`), לפי מחזור החיים של `docs/plan/01-lifecycle-stages.json`.

עד אישור הלקוח, מה שהמערכת יודעת לבד:

| שלב | תוכנית | מתי |
|---|---|---|
| ממתין לסקר | S01 | עבודה שנפתחה ועדיין לא נסקרה בשטח |
| סקר | S02 | נסקר (יש תמונות, או שהסקר מלא מספיק לתכנון), ועדיין אין הצעה |
| הצעה | S03 | יש גרסת הצעה |
| נשלח ללקוח | S04 | יש קישור פעיל |
| הלקוח אישר | S04 | הלקוח אישר גרסה כלשהי בקישור (נשאר גם אם הקישור בוטל אחר כך), או שהמשרד סימן "הסכם נחתם" |

מכאן המשרד מסמן **אבני דרך** בפרטי העבודה, תחת "מחזור חיים":
- סימון ✓ ממלא את תאריך היום, ואפשר לשנות אותו;
- תאריך עתידי נדחה;
- לחלק מאבני הדרך יש שדה אסמכתא (מספר פנייה, קבלה, הזמנה, חשבונית), עד 24 תווים לועזיים.

| שלב | תוכנית | יוצאים ממנו כשמסומן |
|---|---|---|
| הלקוח אישר | S04 | הסכם נחתם · מקדמה התקבלה |
| חח״י ותכנון | S05+S06 | הוגשה בקשה לחח״י · תשובה חיובית מחח״י · תכנון מפורט אושר |
| רכש | S07 | ציוד הוזמן · ציוד הגיע / תואם |
| בהתקנה | S08 | ההתקנה הסתיימה (או צ׳קליסט התקנה נעול) |
| בדיקת בודק | S09 | בודק אישר |
| חיבור מונה | S10 | מונה הותקן · אישור הפעלה מחח״י |
| מסירה | S11 | מסירה נחתמה (או דוח מסירה נעול) · חשבון סופי יצא · ניטור פעיל ללקוח |
| נמסר · שירות | S12 | שלב אחרון |

כללים:
- **הראיה הרחוקה ביותר קובעת.**
  - אבן דרך של שלב מאוחר מעבירה את העבודה אליו.
  - דוח שטח מהגג (יומי, צ׳קליסט, 62446, ליקויים) מעביר ל"בהתקנה".
  - אחר כך מדלגים על כל שלב שכל אבני הדרך שלו מסומנות.
- **מה שנגזר מסומן ככזה:**
  - "תשובה חיובית" מסמנת גם "הוגשה בקשה";
  - "ציוד הגיע" מסמן גם "ציוד הוזמן";
  - דוח נעול מסמן את אבן הדרך שלו.
  - אלה מוצגים עם המקור ולא נשמרים כסימון של המשרד.
- **עבודה שהתקדמה בלי לסמן:** בפרטי העבודה מופיע "העבודה התקדמה בלי לסמן: …". זה המקום להשלים.
- **"הצעד הבא"** בטבלה הוא אבן הדרך הבאה בשלב: "לגבות מקדמה", "לקבל תשובה מחח״י", "להוציא חשבון סופי".
- **בטלפון:** אבני הדרך מגיעות עם שורת המשרד בסנכרון, והצ׳יפ ברשימה מראה את אותו שלב.

מעל השלב המשרד מסמן **סטטוס**: פעיל / מוקפא / לא רלוונטי / סגור, עם הערה קצרה. הסטטוס נשמר בשרת בנפרד מהסקר, ולכן הטלפון לא דורס אותו. הוא חוזר לטלפון בסנכרון הבא ומופיע ליד הסקר ברשימה.

### "דורשות טיפול"

(`src/office/attention.ts` — הספים בראש הקובץ)

- עבודה חדשה בלי סוקר משובץ;
- משובצת בלי מועד סקר יומיים;
- מועד הסקר עבר ואין עדיין סקר;
- סקר בלי הצעה 3 ימים;
- קישור שהלקוח לא פתח יומיים — להתקשר;
- נפתח ולא אושר 5 ימים — לבדוק מה עוצר;
- אחרי האישור, כל אבן דרך מחכה זמן קבוע אחרי הקודמת (`MILESTONE_WAIT_DAYS`). למשל:
  - "הלקוח אישר לפני 9 ימים — לחתום הסכם" (7 ימים);
  - "הוגשה בקשה לחח״י לפני 31 ימים — לקבל תשובה מחח״י" (30 יום);
  - "מסירה נחתמה לפני 8 ימים — להוציא חשבון סופי" (7 ימים).

עבודה מוקפאת / לא רלוונטית / סגורה לא נספרת.

## יומן העבודה

בפרטי העבודה, אחרי "הודעה ללקוח". כל מה שקרה בעבודה, מהחדש לישן, מקובץ לפי יום, עם שעה (שעון ישראל) ומי עשה:

| סוג | מאיפה |
|---|---|
| 🗂 משרד | נפתחה, שובץ / בוטל שיבוץ, מועד סקר, הערה, סטטוס |
| 🏁 אבן דרך | סומנה / עודכנה / בוטלה, עם תאריך ואסמכתא |
| 📋 סקר | הגיע לשרת, ועודכן (גרסה N), ומאיזה מפתח |
| 💰 הצעה | כל גרסה וסכומה |
| 🔗 👀 ✅ קישור | פורסם (ע״י), נפתח (כמה פעמים), אושר (ות״ז אומתה), בוטל |
| 🛠 דוח | טיוטה / ננעל, ותוצאה |
| 💬 הודעה | נפתחה ללקוח, באיזה ערוץ ואיזו תבנית |

רוב היומן נקרא ממה שכבר שמור. מה שהמשרד משנה במקום (סטטוס, הערה, שיבוץ, מועד, אבני דרך) נרשם גם ביומן אירועים נפרד, שורה לכל שינוי, כי שורת המשרד שומרת רק את המצב האחרון. מוצגים 12 אירועים אחרונים, ו"הצג את כל N האירועים" מציג הכול.

## תיק הגשה (חח״י, רשות מקומית, כבאות, בדיקת מתקן, אסדרה)

בפרטי העבודה, מהרגע שהלקוח אישר. השלבים והמסמכים מגיעים מ-`docs/plan/templates/submission-templates.json`, לפי **מסלול האסדרה** של העבודה.

- **מסלול:**
  - מוצע לפי הספק ה-AC בהצעה האחרונה (או ה-DC כשאין AC) וסוג הלקוח:
    - עד 15 kW פרטי → ביתי;
    - 15–100 kW, או עסקי קטן → עסקי/חקלאי;
    - 100–630 kW;
    - מעל 630 kW.
  - "תוספת אגירה" ו"מחלק היסטורי" (קיבוץ/מושב) בוחרים ביד.
  - החלפת מסלול שומרת את מה שכבר סומן.
- **לפי חלקים:**
  - הגשה מקדימה לחח״י, רשות מקומית, כבאות, בדיקת מתקן וחיבור, רישום לאסדרה, היתר הפעלה;
  - החלק של השלב הנוכחי פתוח;
  - רשות מקומית, כבאות והיתר הפעלה אפשר לסמן "לא רלוונטי לעבודה הזו", והם לא נספרים.
- **שלבים:**
  - כל שלב עם מי מבצע (משרד / לקוח / חח״י / קונסטרוקטור…) ועם האגרה כשהיא ידועה בתוכנית (704 ₪ בהגשה הביתית);
  - סימון ✓ ממלא את תאריך היום;
  - לשלבים שיש להם אסמכתא (מספר בקשה, קבלה, מספר מונה) יש שדה.
  - שלבים שהמנוע יעשה לבד (הרצת resolver, מיזוג חבילה, סגירה) לא מוצגים, אבל המסמכים שלהם כן.
- **מסמכים:** החובה, ואחריהם "(אם נדרש)", עם מי חותם. למעלה מוצג "N/M שלבים · N/M מסמכים" ורשימת המסמכים החסרים.
- **בלי הקלדה כפולה:** שלב שהוא אותה עובדה כמו אבן דרך מסמן גם אותה, אם עוד לא סומנה. "מסמן גם אבן דרך" מופיע ליד שלבים כאלה:
  - הגשה ב-digitalorders → "הוגשה בקשה לחח״י" (עם מספר הבקשה);
  - תשובת מחלק → "תשובה חיובית";
  - מונה → "מונה הותקן";
  - אישור הפעלה → "אישור הפעלה".
- **יומן:** כל סימון נכנס ליומן העבודה.

## פרטי החברה

מסך משרד → **הגדרות** (מנהל בלבד) → "פרטי החברה": מותג, שם, ח״פ (נבדקת ספרת ביקורת), רישיון, כתובת, טלפון, מייל ואתר. **שום פרט לא ממולא מראש מלבד השם**, ושדה ריק לא מוצג.

| איפה | מה |
|---|---|
| דף הלקוח | לוגו בראש הדף (`/brand/bee-logo.png`, על רקע בהיר). בתחתית: שם, ח״פ, רישיון, כתובת, טלפון לחיץ, מייל ואתר |
| "איפה הפרויקט עומד" | "לשאלות — התקשרו אלינו" עם הטלפון |

| הודעה ללקוח | "הטלפון שלנו" ממולא מטלפון החברה, אם לא הוקלד אחר |

## דף הלקוח אחרי האישור

אחרי שהלקוח אישר, אותו קישור (`/q/<token>`) מראה גם **"איפה הפרויקט עומד"**:
- השלבים מ"הסכם ומקדמה" עד "ניטור ותחזוקה", בתוויות ללקוח מהתוכנית (`customer_visible_label_he`), עם ✓ ותאריך לשלב שהושלם;
- משפט אחד על מה קורה עכשיו (`CUSTOMER_NOW_HE` ב-`src/stage.ts`), בלי הבטחת זמנים.

השלב נגזר בדיוק כמו במסך המשרד, כלומר מאבני הדרך, תיק ההגשה והדוחות, ולכן הדף מתעדכן לבד.

**מה לא מוצג:** הערות, אסמכתאות (מספר בקשה, קבלה, הזמנה), שמות של אנשי המשרד. עבודה "מוקפאת" מציגה "הפרויקט בהמתנה". עבודה "לא רלוונטית" או "סגורה" לא מציגה התקדמות.

כך כל הודעה ללקוח עם הקישור (`portal_link` בתבניות) מובילה גם למצב הפרויקט.

## הודעה ללקוח

בפרטי העבודה, אחרי "מחזור חיים". התבניות הן אלה של `docs/plan/templates/message-templates.json`: אותם מפתחות ואותו נוסח שהמנוע ישלח בהמשך דרך Meta, ולכן המעבר יהיה מיפוי ולא כתיבה מחדש.

1. **בחירת תבנית.** קודם מוצגות התבניות של השלב הנוכחי ("מתאים לשלב"), ואחריהן כל השאר. ברירת המחדל היא העדכון של אבן הדרך האחרונה שסומנה ועוד לא נשלחה עליה הודעה. למשל, אחרי "הוגשה בקשה לחח״י" מוצעת "הבקשה הוגשה לחח״י" עם מספר הבקשה.
2. **מילוי מהעבודה.** מה שידוע כבר ממולא:
   - שם, כתובת, kWp, גרסה ותוקף ההצעה;
   - הקישור ללקוח;
   - מספר בקשה בחח״י ומספר חשבונית, מאבני הדרך;
   - סוקר ומועד סקר;
   - מספר תיק `BEE-XXXXXX`, קבוע לכל עבודה ונגזר ממזהה הסקר.

   מה שחסר מקבל שדה מסומן, והכפתורים נעולים עד שהוא מתמלא. כך לא תצא ללקוח הודעה עם `[מועד 1]`. השם והטלפון שלנו נשמרים בדפדפן להודעה הבאה.
3. **עריכה.** אפשר לערוך את הטקסט ביד לפני השליחה.
4. **שליחה (Law #2).** **וואטסאפ / SMS / מייל** פותחים את האפליקציה עם ההודעה מוכנה, ואתם לוחצים שלח:
   - SMS רק לנייד;
   - מייל רק כשיש כתובת;
   - שום דבר לא נשלח מהשרת.
5. **יומן.** כל פתיחה נרשמת תחת "הודעות שנפתחו": מה, באיזה ערוץ, מתי, מי, והטקסט המלא. "נפתח" הוא כל מה שהמערכת יכולה לדעת. את השליחה עצמה עושה אדם.

לא מוצגות כאן תבניות של קוד אימות וקישור לפורטל (עוד אין פורטל), וגם לא הודעות לספקים או פנימיות.

## כרטיס לקוח בסקר

בטופס הסקר, אחרי "פרטים כלליים", יש פרק **לקוח**: שם, טלפון, מייל, ת״ז / ח״פ, סוג לקוח (פרטי / עסקי). הכול רשות, ואפשר להשלים אחרי הסקר. האפליקציה מזהירה ולא חוסמת: חסר שם, טלפון לא ישראלי, מייל לא תקין, ספרת ביקורת של ת״ז שגויה.

לאן זה זורם:

- **הצעה ו-PDF:** "לכבוד <שם>", ושם הלקוח בדף ההצעה אונליין.
- **וואטסאפ:** אחרי פרסום קישור יש כפתור **"וואטסאפ ל<שם>"**. הוא פותח את וואטסאפ עם המספר וההודעה מוכנה, והסוקר לוחץ שלח (Law #2: אין שליחה אוטומטית ללקוח).
- **אישור אונליין:** כשיש ת״ז בסקר, 4 הספרות שהלקוח מקליד חייבות להתאים להן:
  - אחרי 5 ניסיונות שגויים הקישור ננעל לאישור;
  - האישור נשמר עם "ת״ז אומתה";
  - בלי ת״ז בסקר כל 4 ספרות מתקבלות, והאישור מסומן "לא נבדקה".
  - הת״ז עצמה לא נשלחת לדף הלקוח. לשרת נשלחות רק 4 הספרות האחרונות, ליד ההצעה ולא בתוכה.
- **דוחות שטח:** שם הלקוח ממולא מהסקר.
- **רשימה ובמשרד:** שם וטלפון לחיץ, וחיפוש לפי טלפון.

## מפתחות אישיים ותפקידים

עד עכשיו היה מפתח אחד (`PUBLISH_KEY`) בכל הטלפונים. עכשיו:

| תפקיד | מה מותר |
|---|---|
| **סוקר** | גיבוי סקרים, תמונות, הצעות ודוחות, פרסום קישור ללקוח, שחזור לטלפון חדש |
| **משרד** | כל זה + מסך המשרד, סטטוס והערה, feed הכוורת (`/api/hive/jobs`) |
| **מנהל** | כל זה + יצירה וביטול של מפתחות |

- `PUBLISH_KEY` הוא **המפתח הראשי** (מנהל). הוא ממשיך לעבוד כמו קודם, ולכן שום דבר לא נשבר. עדיף שיישאר רק אצל ברק.
- **יצירה:** מסך משרד → "מפתחות" → שם + תפקיד → "צור מפתח". המפתח (`bee_…`) **מוצג פעם אחת**. מדביקים אותו בטלפון של הסוקר: מחירון → שרת החברה → מפתח.
- **טלפון אבד:** "בטל" ליד המפתח שלו. הטלפון הזה מפסיק לגבות ולפרסם מיד, וכל השאר ממשיכים לעבוד.
- **בשרת נשמר רק sha256 של המפתח** (`auth/keys/<sha256>`). רשימת המפתחות מראה שם, תפקיד, מי יצר ו-4 תווים אחרונים.
- **"בדיקת חיבור לשרת"** במסך המחירון אומרת עכשיו גם של מי המפתח ("המפתח תקין — דני (סוקר)").
- **מי עשה מה:** כל סקר שמגיע נרשם עם שם המפתח ששלח אותו (`receivedBy`), וכל קישור עם מי שפרסם (`published_by`).

## API (חדש)

| נתיב | תפקיד | מה |
|---|---|---|
| `GET /api/me` | כל מפתח | של מי המפתח |
| `GET /api/office/overview` | משרד | כל העבודות: שורת סקר + לקוח + `stage` + `office` + `milestones` (כולל הנגזרות, עם `auto`) + `latestQuote` + `links` (צפיות, אישור) + `reports` + `lastActivityAt` |
| `PUT /api/office/status/<surveyId>` | משרד | כל אחד מ-`{ status, note, assigned_to: <id מפתח>\|'', planned_date: YYYY-MM-DD\|'', milestones: { <אבן דרך>: { date, ref? } \| null } }`. משתנה רק מה שנשלח. `null` מבטל אבן דרך |
| `POST /api/office/jobs` | משרד | עבודה חדשה: `{ customerName, customerPhone, address, customerEmail?, projectName?, note?, assigned_to?, planned_date? }` → `{ id, office }` |
| `GET /api/company` | ללא מפתח | פרטי החברה הציבוריים |
| `PUT /api/office/company` | מנהל | שמירת פרטי החברה, עם ולידציה |
| `GET /api/office/submission/<surveyId>` | משרד | `{ submission \| null, suggested: { id, why_he } }` |
| `PUT /api/office/submission/<surveyId>` | משרד | `{ track?, steps?: { <שלב>: { date, ref? } \| null }, docs?: { <מסמך>: { date } \| null }, na?: [mun\|fire\|op] }`. מחזיר `{ submission, office }`, ו-`office` רק כשאבן דרך סומנה |
| `GET /api/office/timeline/<surveyId>` | משרד | יומן העבודה: `{ events: [{ at, kind, text_he, by, tone? }] }`, מהחדש לישן |
| `GET /api/office/messages/<surveyId>` | משרד | הודעות שנפתחו ללקוח, מהחדשה לישנה |
| `POST /api/office/messages/<surveyId>` | משרד | `{ template_key, channel: whatsapp\|sms\|email, to, subject?, body }`. רק רישום, לא שליחה |
| `GET /api/office/surveyors` | משרד | מי אפשר לשבץ: מפתחות פעילים (שמות בלבד) |
| `GET /api/office/keys` | מנהל | רשימת מפתחות (בלי המפתחות עצמם) |
| `POST /api/office/keys` | מנהל | `{ name, role }` → `{ key, row }`. המפתח מוחזר פעם אחת |
| `DELETE /api/office/keys/<id>` | מנהל | ביטול (נשמר לתיעוד) |

`GET /api/surveys` מחזיר לכל סקר את `office` ואת `assigned_to_me`, כלומר אם העבודה שובצה למפתח ששאל. כך הטלפון מושך את העבודות שלו.

`POST /api/quotes` מקבל עכשיו גם `survey_id` ו-`customer_id_last4`. שניהם פרטיים: נשמרים ליד ההצעה ולא בתוכה. `PUT /api/surveys/<id>` מחזיר את `office`, וכך הסטטוס מגיע לטלפון.

## אחסון ב-R2 (חדש)

```
auth/keys/<sha256>                  מפתח אישי (customMetadata: שם, תפקיד, נוצר, בוטל, 4 תווים אחרונים)
office/<surveyId>                   סטטוס משרד, הערה, סוקר משובץ, מועד סקר ואבני דרך (ms="cs=20261020,is=20261022~7004512")
quote-links/<surveyId>/<token>      כל קישור שפורסם לסקר (נשאר אחרי ביטול, עם revoked_at)
quotes/<token>/accept-fails.json    ניסיונות אישור עם ספרות שגויות
messages/<surveyId>/<iso>_<rand>.json  הודעה שנפתחה ללקוח (אובייקט לכל הודעה, בלי דריסה)
events/<surveyId>/<iso>_<n><rand>.json שינוי של המשרד בעבודה (שורה ליומן)
submission/<surveyId>.json            תיק ההגשה: מסלול, שלבים, מסמכים, חלקים לא רלוונטיים
settings/company.json                 פרטי החברה
```
